# Independent resource and infrastructure review (2026-11-05)

Scope: distributed abuse admission and export leases, Media upload/read/delete capabilities, API/worker filesystem and outbound-request boundaries, dependency advisories, and repository infrastructure configuration. This review reads actual source and runs bounded local tests; previous audit claims are not evidence. No production request, provider mutation, deployment, or migration was performed. A fresh disposable PostgreSQL server on loopback port 55469 was supplied for tests, which create and drop their own databases.

## RES-01 — Medium — Analysis deletion released a still-live upload capability's storage reservation

**Location:** `backend/modules/Media/Metrivum.Media/MediaLibrary.cs`, `ReleaseVideoAsync`; caller: `backend/modules/VideoAnalysis/Metrivum.VideoAnalysis/AnalysisLibrary.cs`, `DeleteAsync`.

**Cause:** deleting the last analysis called the owning Media contract to unpin its source and set `DeleteAfter` immediately. Ordinary and portfolio deletion correctly wait for `UploadExpiresAt`. Cleanup could therefore physically delete that source and mark its row `Deleted` before its signed upload URL expired. Deleted rows no longer reserve the global storage budget. A signed non-upsert capability can create an absent object again; it does not provide application-row revocation.

**Abuse:** obtain a valid video ticket, finalize and use it as an analysis source, delete the last analysis, wait for cleanup, and reuse the original upload URL before expiry. This permits an orphan object outside active global accounting and cleanup, and potentially more bytes than the verified original file. It does not grant access to another owner's object. Account/day start limits still bound the rate of issuing new tickets; they do not repair orphan accounting across days.

**Evidence:** new PostgreSQL regression `Released_analysis_video_retains_storage_liability_until_upload_capability_expires` failed before the fix: immediate cleanup returned **1**, expected **0**, at its first cleanup assertion. This exercises actual migrations, EF updates and cleanup selection; the storage adapter is a fixture. The regression is green after the fix and also verifies that another owner cannot spend the retained global reservation, then verifies cleanup and admission after simulated expiry. Provider-level upload replay was **UNVERIFIED** because no disposable local Supabase Storage instance was available. The replay scenario follows the capability's signed expiry/object binding, rather than a claim of a live provider exploit. See [Supabase Storage token implementation](https://github.com/supabase/storage/blob/master/src/storage/object.ts).

**Fixed locally:** set analysis-source deletion time to `max(now, UploadExpiresAt)`, matching generic/portfolio deletion. Cleanup independently requires expired upload capability, protecting unsafe `Deleting` rows queued by earlier releases. New legacy-row regression also failed before that central guard (cleanup **1**, expected **0**). No schema, HTTP contract or permission change. Existing Ready and Pending accounting remains in place. This fix does not retroactively discover orphaned objects created before deployment; reconcile the private bucket against Media rows using a reviewed read-only inventory before deciding on cleanup.

## RES-02 — Medium — Shared document viewers spent the author's download allowance

**Location:** `backend/modules/Media/Metrivum.Media/DocumentMedia.cs`, `ReadDocumentAsync`; caller: `backend/modules/ClientDocumentation/Metrivum.ClientDocumentation/DocumentationService.cs`, `ReadFile`; internal boundary: `Media.Contracts/IDocumentMedia.cs`.

**Cause:** documentation read authorization correctly resolved the current viewer and checked participant/visibility/relationship access, but Media charged `SignedDownload` against `ownerId` (the document author). An authorized peer could consume the author's shared download allowance, including its allowance for other files. Generic shared-media and portfolio reads already charge the viewer.

**Abuse/impact:** a client repeatedly requests a coach-authored shared document, spending the coach's download quota and causing 429 for the coach; a coach reading client-authored documents could similarly affect that client. Multiple authorized clients can aggregate consumption against one author. Other write/global limits remain in force. This is a cross-account availability issue, without access to unauthorized contents.

**Evidence:** `Shared_document_downloads_charge_the_viewer_without_spending_the_authors_budget` uses the actual PostgreSQL Documentation/Coaching/Media services and a real local limiter configured to one signed download. After the authorized peer's first read, the author's first read failed with `RATE_LIMIT_EXCEEDED` before the fix. The test runs both author/viewer role directions and verifies the peer's own second read is rejected before another signed URL is issued. Storage transport is a fixture; the quota attribution is not mocked.

**Fixed locally:** pass authenticated `account.UserId` through the internal document media contract as `viewerId`, and charge that identity. The owner still selects the object and is separately checked. The trusted calling service supplies viewer identity, not an HTTP payload. No schema, public HTTP/generated contract, or production setting changed.

## Admission and lease attack results

| Attempt / invariant | Observed result | Evidence and limits |
| --- | --- | --- |
| Spend one owner's allowance over independent API/store instances; change OAuth client/scope identifiers | Shared cap holds; identifiers do not create counter partitions | `Independent_instances_and_restarts_share_atomic_allowances_per_owner_and_operation`: 30 simultaneous attempts, exactly 7 accepted; restart still rejects; distinct user/policy isolated |
| Refund a charged attempt by rolling back its business transaction | Rejected | Separate autocommit store connection retains admission; rollback/expiry test passes |
| Reset a burst completely after one refill period | Rejected | Actual PostgreSQL refill test exhausts 4, ages one period, admits 2 and rejects the third; very old timestamp does not overflow |
| Keep two export operations active, cancel one request and immediately acquire another slot on another instance | Rejected until real disposal | Export lease cancellation/disposal regression; PostgreSQL transaction advisory slots remain held until lease disposal |
| Saturate lease pool and starve rate counters | Bounded rejection | Eight operation slots, ninth denied; independent counter pool still admits |
| Reuse upload routes/owners to exceed pending, daily, or global reservation budgets | Atomic rejection | Media tests cover 12 simultaneous mixed-route starts, cross-owner global admission and exact daily/hourly boundaries |
| Fail object validation, delete and restart to refund daily liability | Rejected | Underdeclared failed upload regression retains maximum-bucket reservation even after deletion |
| Obtain a signed capability before its reservation commits | Rejected | Database failure regression observes no signer call; failed signer leaves durable reclaimable reservation |
| Get a read URL for an object with changed size, MIME or prefix | Rejected by source validation | Media validates exact actual bytes/size/MIME before readiness/read; attachment validation includes MIME plus signature and bounded WAV duration parsing |

These are local PostgreSQL/module/HTTP tests, with fixture storage. They are not Storage-provider or production load tests. Counter policy names are server constants; scope/client IDs are deliberately ignored by the user budget, and concurrency keys use verified user + policy + bounded slot number. `PostgresAbuseCounterStore` uses a private 4-connection admission pool and a separate 8-connection operation pool. Conditional upsert serializes against the unique owner/policy row; no shared `ModuleTransaction` connection is parallelized. Store errors fail the operation rather than falling back to a fresh local quota.

**Remaining boundaries:** global HTTP, ordinary read, anonymous and SignalR budgets are local to each process. They multiply across replicas/restarts. Identity admission is capped and rejects new identities at saturation, which bounds memory but can deny legitimate newcomers until capacity returns. Provider ingress controls, verified proxy trust, capacity alerts and multi-replica soak remain deployment gates. Export locks also release if the database connection/server dies while a synchronous render continues; process cancellation is not a CPU sandbox. No DB-restart render test was performed. The public readiness endpoint's unmetered database work is separately flagged to the host auditor.

## Media, SSRF, path and decoder boundaries

Media keys are generated from server-owned user/resource GUIDs and fixed subdirectories; client filenames do not determine filesystem or object paths. Storage operations use a configured provider URL, exact configured bucket and escaped object segments, not an arbitrary client URL. Workflow-owned documentation/portfolio files are excluded from generic readable-file paths, with relationship/purpose prefixes checked by their owning contracts. No client-driven arbitrary HTTP, SQL or shell execution was found on these Media paths. This is a source-traced result, not a whole-repository absence proof.

Storage signing checks the bucket is private and has a positive configured maximum; `x-upsert: false` is requested. These adapter assertions pass with synthetic HTTP responses. Actual bucket privacy/RLS/grants, overwrite rejection, same-token replay after deletion, content-length enforcement and signed URL expiry remain **UNVERIFIED** on Supabase. A signed read URL remains a bearer capability for its configured 30–600 second expiry after application authorization is revoked. Direct upload tickets can temporarily upload the bucket maximum rather than the declared per-ticket size; reservations account for this physical maximum, but do not cap repeated failed upload network traffic. Service-only Storage mutations and immutable objects are prerequisites.

The API's MotionTrace bridge generates a random work directory and fixed filenames, passes process arguments with `ArgumentList` and `UseShellExecute=false`, bounds source and result bytes, drains process output without retaining it, and kills the process tree on cancellation. Its environment excludes application credentials. It is **not** an OS/network sandbox: malformed media decoder exploitation and network/file isolation require worker/container policy and device/model validation. No hostile codec execution or device test was performed.
