## AUTH-01 — stale successful Auth requests replace a different account lifetime

- Severity: **Medium**. Status: **fixed locally**.
- Original locations: `apps/web/app/modules/auth/routes/login.tsx` password response handling; `register.tsx` signup response handling; `verify.tsx` OTP completion; `callback.tsx` session exchange; `mfa.tsx` initial refresh; `components/SecondFactorForm.tsx` challenge completion. The persistent client was created in `apps/web/app/shared/session/supabase.ts:19`.
- Root cause: the installed `@supabase/auth-js` 2.117.2 runs `_saveSession` and `SIGNED_IN` notification before `signInWithPassword` resolves (`node_modules/@supabase/auth-js/src/GoTrueClient.ts:1277`). Checking the form generation only after the SDK call cannot prevent its localStorage/broadcast side effects. OTP/callback/MFA callers also lacked complete post-request lifetime checks.
- Reproduction: sign in A in slot 0 and B in slot 1; begin a delayed successful C password sign-in targeting slot 0; switch to B; return C's successful Auth response; deliberately skip `completeSignIn` using the form's existing generation guard. Before the fix, slot 0 persisted C and its Auth event replaced A in the manager. The real SDK regression initially failed with stored subject `33333333-3333-4333-8333-333333333333` instead of `11111111-1111-4111-8111-111111111111`.
- Impact: an abandoned/replaced login or verification can change the account saved in a slot, restore an unintended account on reload, or reactivate a previous account after MFA refresh. This is account/session confusion; no authorization escalation into an account without valid Auth credentials was demonstrated.
- Fix: `supabase.ts:48` creates disposable candidate clients with isolated SDK coordination and a storage adapter mapped to the original slot's session/PKCE keys. At the actual synchronous session write it validates the lifetime, expected email/user ID, and original slot identity. A stale candidate cannot write, remove another session or broadcast a successful session. Accepted events use the slot's existing BroadcastChannel; disposal closes SDK resources without signing out the accepted account. `manager.ts:190` supplies this boundary and `manager.ts:204` checks lifetime before accepting sign-in state. Auth callers pass the relevant identity and dispose candidates. MFA refresh and success handlers check account generation before continuing.
- Regression evidence: `apps/web/app/shared/session/auth-attempt.race.test.ts` runs the installed SDK against controlled Auth responses for password, signup, OTP, PKCE, MFA and refresh. Each successful request is held in flight, the account changes, and the response is released. Valid-flow controls prove the candidate still persists the correct session and disposal preserves it. Additional cases cover substituted callback identity, native Node BroadcastChannel delivery/suppression, a late competing candidate before its auth event arrives, and primary A refresh finishing after accepted C sign-in. `apps/web/app/modules/auth/routes/mfa.test.tsx` checks that stale refresh/code completions do not call their success handlers. The browser regression navigates away while successful Auth is in flight and checks A remains stored.

## Negative checks and retained boundaries

- Turnstile component tests reject direct form submission without a token, second consumption, expired/error tokens, stale widget callbacks, missing required keys and production dummy keys. Installed SDK transport tests cover all five issuance flows. Browser tests verify signup/password/OTP/reset/resend pass `gotrue_meta_security.captcha_token`; a visible widget is not treated as proof of provider enforcement.
- The production default is CAPTCHA-required. `VITE_AUTH_CAPTCHA_REQUIRED=false` with no site key remains an explicit documented initial rollout override in `auth/lib/turnstile-config.ts:4`. It can remove browser gating in a production build; it cannot disable Supabase enforcement. This is an operational acceptance gate, not evidence that production is protected. Require the intended public key/flag and separately verify Supabase CAPTCHA before public launch.
- Developer mock Auth is guarded by `import.meta.env.DEV` in `shared/dev/mockMode.ts:6`; the development mock flag alone does not enable it in a production build.
- OAuth consent identity/callback/grant choices come from the API, not spoofed query strings. `integrations/consent.tsx:15` rejects off-origin/off-path, non-HTTPS non-loopback and credential-bearing redirects. `integrations/api.ts:35` rejects stale mutation success callbacks. Tests check selected-only grants, explicit user approval, expired actions and stale account mutation results.
- `AccountScope` uses slot/user query prefixes, aborts the previous lifetime synchronously, and binds access tokens to the expected user. Existing session/account/workspace tests passed. Coach/Client mode is presentation state; server authorization remains a separate owning-module responsibility.
- Scoped searches of Auth/session/integrations found no raw HTML/eval sink or application log of Auth tokens/passwords. This is a source review of these modules, not a repository-wide secret-scan result. Normal API bearer authentication and browser-bound callback nonce validation were inspected; no additional CSRF bypass was reproduced in this scope.
